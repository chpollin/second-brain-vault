Make the route from a task through its checks and decisions to result acceptance or workflow revision explicit and supported by evidence.

## Reads

Resolve vault paths against the verified vault root and skill resources against this folder. Inspect available tools and access before promising repository or execution checks.

- The supplied task and workflow material. For a new design, use the stated requirements and constraints.
- For an existing workflow, `Vault Operations/Conventions/Convention Knowledge Documents.md` and the selected project instructions, knowledge and implementation or issue records. Use `Vault Operations/Repo Directory.md` only to resolve an unknown project location.
- `Vault Operations/Conventions/Convention Curation Round.md#Write boundaries` before a file edit, and `.claude/skills/writing-style/SKILL.md` before prose delivery.

Read only what answers the current workflow question. Sufficient supplied material requires no unrelated project sources. A new design does not require an existing repository. If an implementation source is unavailable, report which claims remain unchecked. An unreadable binding rule stops the dependent change.

## Procedure

1. Follow the requested task. For an explanation, describe the supported workflow without adding a redesign. For a review, identify supported defects and propose only justified corrections. For a new design, derive a proposed sequence from the stated constraints and label assumptions. Preserve accepted decisions and do not demand execution evidence for a system that has not been built.
2. Trace a representative task through context, actions, returned results and decisions. For each consequential transition identify its condition and who or what can trigger it. Distinguish the agent's action selection, the harness's execution and the surrounding human work. An existing workflow needs source locations for claimed transitions. A design needs stated requirements for proposed ones.
3. Make checks and authority explicit. State what a check examines, against which criterion, and what its result permits. Automatic execution is distinct from a deterministic criterion. LLM review and domain acceptance need separate attribution. Preserve the documented order of decisions. Required acceptance alone does not imply acceptance before technical integration or merge. An explicit pre-merge condition does. Roles may overlap in one person, while agent coordination alone grants no authority to accept results or expand scope. Mark unresolved responsibility instead of inventing an appointment.
4. Follow feedback to its consequence. Distinguish correction of the current result, a new requirement and a change intended to affect future work. Record only the evidence, affected scope and recheck needed to follow that consequence. These consequences can coexist. Preserve rejected and unresolved outcomes. Define when work continues, stops or returns for a decision, including repeated failure. A documented rule change needs separate evidence of later application and benefit. Comment counts and calendar time alone establish neither effort nor quality.
5. Match the output to the request. A review or design includes the smallest justified change and how it can be checked. Do not add scoring, extra agents or review stages without a stated need. A structured design may use a compact transition table. A short explanation needs no additional apparatus. In a requested diagram show only the transitions required for the question and put supporting detail in the accompanying prose.

## Boundaries

Apply the current authorisation and `Convention Curation Round.md#Write boundaries`. Design and review alone do not authorise implementation, issue closure or deployment. No agent assessment establishes human acceptance. Confidential project examples stay in their authorised location and never enter public skill fixtures.

## Verification

Check every claimed transition against its actual source. Label statements supported only by instructions, code inspection or an observed run accordingly. Recheck whether an accepted result and a future workflow change have distinct grounds. Read back authorised file edits and run the destination's applicable checks. Apply the loaded style self-check.

Maintenance cases are in [evals/test-cases.md](evals/test-cases.md). A reading exercise establishes interpretation of these instructions, not successful runtime behaviour or scholarly acceptance.

## Output

Return a compact account of the workflow and its evidence. Use a table when comparing transitions, checks or responsibilities. Separate supported findings from proposed changes and name the smallest missing source or decision. Report exactly which sources and behaviour were checked.
